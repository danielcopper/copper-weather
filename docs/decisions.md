- D26 (2026-11-19): The refresh token is sealed with AES-256-GCM under a key that stays in the Android Keystore, and kept with the address and the `client_id` in the app's private preferences; androidx.security's EncryptedSharedPreferences is deprecated in favour of the Keystore used directly. The key needs neither user authentication nor an unlocked phone, so a fetch in the background can use it. The access token is never stored. When the token of a new sign-in cannot be sealed, the app asks Home Assistant to end it again, keeps nothing, and the sign-in fails (D25). A stored sign-in that cannot be opened (its token sealed with another key or changed, too short or not Base64, or a field missing) counts as lost, and signing in again is the only way on; a failure of the Keystore or the cipher that may pass does not. Nothing is backed up or moved to a new device.

- D29 (2026-11-20): The snapshot (D2) is one JSON file in the app's files, written whole through `AtomicFile`, so a reader finds the old one or the new one: the app sensor's attribute `data` as Home Assistant sent it, a field without a value left absent as it is there, and when it was fetched. - D30 (2026-11-20): The app reads only the app sensor's schema version 1 (owner, 2026-11-20). Data with another version is not taken: the fetch counts as failed and the last snapshot stays. - D31 (2026-11-20): A fetch, keeping a new sign-in and forgetting a signed-out one share one lock, as in copper-calendar: a sign-out or a new sign-in waits for a fetch that runs, so its snapshot does not outlive the sign-in it was fetched with; a new sign-in deletes the snapshot and the last failure of the one before; without a usable sign-in a fetch stops the periodic fetch while it holds the lock, so it cannot stop the fetches of a sign-in that comes meanwhile. Signing out stops the fetches before and once more after it, so a fetch scheduled while it waits does not outlive it, and deletes the snapshot and the last failure; the fetch interval stays (D28). The second stop and the widget's update run also when the sign-out fails. A snapshot that is still on the phone after its deletion makes the sign-out fail; a new sign-in deletes the snapshot before it keeps anything, so when that fails it keeps nothing, leaves the account as it was and asks Home Assistant to end its token. So a snapshot left behind never shows as a later sign-in's; while no one is signed in the widget and the screen show none of it (D32, D33). The sign-in's start and end live in the fetch's class, beside the fetch, so the lock is one class's own.
- D32 (2026-11-20): Besides signed in and signed out, a sign-in can be refused or unreadable, as in copper-calendar (its D45, D46, D52). Both show the address form to sign in again, and no fetch runs until then. The snapshot's attribution (D18) shows on the screen while there is a snapshot and someone is signed in, also beside a refused or unreadable sign-in, since the widget still shows its weather; not while signed out, when a snapshot left behind is no one's (D31).
